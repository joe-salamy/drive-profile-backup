## Behavior Changes
- **Backup**: When `encrypt_secrets: true` (default), every file matching secret patterns (`.env`, `credentials.json`, `token.json`, `id_rsa*`, `id_ed25519*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `.boto`, `.claude.json*`, etc.) or inside `.ssh`/`.azure`/`.gemini`/`.android`/`.aitk`/`.cisco` is encrypted client-side with AES-256-GCM (random 12-byte nonce, 32-byte key) and uploaded as `relative/path/file + ".enc"` under same Drive folder hierarchy; `Drive md5Checksum` (ciphertext) is ignored, manifest stores plaintext MD5 and `encrypted: true`; second run dedups on plaintext MD5+mtime+size, re-uploads if `encrypted` flag mismatches; key file at `~/.drive-backup/secrets.key` (default) is generated once with `0o600` and displayed in a high-visibility Rich panel (hex + base64) with warning that it is shown only once; missing key during backup (non-dry) skips encrypted files with `encrypted_missing_key` error, never uploads plaintext; dry-run with missing key counts encrypted files as `WOULD_UPLOAD (encrypted, key will be generated)` without creating key; size limits still apply to secrets (exceeds → skipped, not encrypted); `.drive-backup` remains excluded and never encrypted/uploaded
- **Restore**: `drive-backup --restore --output DIR` auto-decrypts when key exists at `secrets_key_path` (or `--decrypt-key`); uses stored `drive_file_id` (ciphertext) directly, decrypts to original `relative_path` with `0o600` for secrets dirs; when key missing and `decrypt` true, downloads ciphertext as `*.enc` with warning and synthetic error entry, does not attempt decrypt; `--no-decrypt` keeps `.enc` even if key present; `--decrypt-key` overrides path; `dry_run` counts files without downloading; `force` overwrites existing; unsafe paths and missing Drive IDs still fail
- **CLI**: `--no-encrypt-secrets` disables encryption (secrets then follow normal exclusion, i.e. skipped if in `exclude_dirs` else plaintext); `--decrypt`/`--no-decrypt` control restore; `--decrypt-key` specifies key for restore or for `--generate-secrets-key`; `--generate-secrets-key` generates/loads key and prints panel then exits without backup/restore
- **Config**: Old `config.yaml` without new keys loads with defaults (`encrypt_secrets=True`, `secrets_key_path="~/.drive-backup/secrets.key"`), so next run enables encryption intentionally; unknown keys still rejected
- **Manifest**: Old manifests without `encrypted` load as `encrypted=False`; new manifests roundtrip `encrypted` via `asdict`; `encrypted` is optional bool, not required, so backward compat preserved
- **Report**: JSON report now includes `files_encrypted_uploaded`, `bytes_encrypted_uploaded`, `total_size_encrypted_human`; CLI summary table shows `Files encrypted` / `Size encrypted` row when non-zero

## Implementation Decisions and Tradeoffs
- **Cryptography lib**: chose `cryptography` (AESGCM) over `PyNaCl` because plan specifies it, wheel available on Windows, no system OpenSSL build needed; `KEY_BYTES=32`, `NONCE_BYTES=12`, `FILE_VERSION=b"\x01"` for future versioning
- **Key storage**: raw 32 bytes via `mkstemp` + `chmod 0o600` + `os.replace` for atomicity and restrictive perms; `load_key` supports raw/hex/base64 to tolerate manual copy-paste; `load_or_generate_key` ensures parent dir exists, handles Windows chmod best-effort (no ACL API), uses `os.urandom` via `AESGCM.generate_key`
- **Scanner precedence**: `is_secret` bypasses `exclude_files`/`exclude_path_patterns`/`exclude_specific_files` but **not** symlink or size limits; this matches plan (“exceeds_size_limit still skipped”); `.drive-backup` stays excluded because not in `SECRETS_DIR_NAMES`; allowed descent into secrets dirs even when in `exclude_dirs` via guard `if config.encrypt_secrets and _is_secret_dir(d): append and continue`
- **Manifest invariant**: `ManifestEntry.md5` is always **plaintext** MD5 for encrypted entries; Drive `md5Checksum` (ciphertext) ignored for dedup; this enables content-based dedup without decrypting; `encrypted` flag mismatch forces `content_changed` re-upload because Drive filename changes (`.enc` suffix)
- **Engine temp file naming**: initial `mkstemp(suffix=".enc")` gave random Drive name (bug); fixed to `mkdtemp(prefix="enc-")` + `os.path.join(tmpdir, filename_enc)` so `drive_api.upload_file` (which uses `Path(local_path).name`) uploads with correct `*.enc` name; cleanup via `unlink` + `rmdir` in `finally`; resumable threshold uses ciphertext size (`os.path.getsize(enc_path)`)
- **Stats**: added `files_encrypted_uploaded`/`bytes_encrypted_uploaded` to `BackupStats` and `BackupReport`; engine increments in both dry-run (`_prepare_upload`) and real (`_complete_upload`); `_record_upload` unchanged (still records `relative_path` as original, `extension` as original)
- **Key display**: Rich `Panel` + `Text` with title `[bold red]NEW SECRETS ENCRYPTION KEY — COPY AND SAVE NOW[/]`, body `Path:`, `Hex:`, `Base64:`, warnings, logged via `logger.warning`; only when `was_generated` and not `dry_run`; also shown for `drive-backup --generate-secrets-key` helper (green border if existing)
- **Restore**: uses `entry.encrypted` flag, not filename suffix, to decide decrypt; downloads via `drive_file_id` directly; decrypt failure raises `ValueError("decryption failed: ...")` and records `files_failed`; missing key path handled via `os.path.exists` + `load_key`, synthetic error `<secrets-key>` added to `errors` but not counted as `files_failed`; `chmod 0o600` for secrets dirs on POSIX; `dry_run` and `--no-decrypt` both result in `.enc` suffix
- **Config**: `encrypt_secrets` boolean validated with `type(value) is bool`; `_STRING_LIST_FIELDS` bug fixed (missing `values[field_name]=value`); `collectors` validation restored; old configs default to `True` to enable encryption on next run intentionally
- **CLI**: `--decrypt`/`--no-decrypt` share `dest="decrypt"` with `set_defaults(decrypt=True)`; `--generate-secrets-key` is early-exit after `load_config` and override handling, does not trigger backup/restore; `args.decrypt_key` overrides key path for both restore and generate
- **Test updates**: `tests/test_report.py` expected tuple extended with 3 new keys; `tests/test_cli.py` restore lambda extended to accept `decrypt`/`decrypt_key_path` kwargs to match new `restore_backup` signature; both required for existing tests to pass with new behavior

## Assumptions
- Key file default `~/.drive-backup/secrets.key` is acceptable and never uploaded (explicitly kept excluded even when `encrypt_secrets` true; `.drive-backup` dir remains in `exclude_dirs` default)
- Secrets rarely exceed `max_file_size_mb` (500 MB default, plan mentions 150 MB); if they do, skipped with `exceeds_size_limit` rather than truncated; user can raise limit or add `no_size_limit` ext
- Secrets size < `max_file_size_mb` and whole-file read is okay (no streaming); documented limit in `crypto.py` docstring
- `cryptography` wheel available on target Windows (pure-Python wheel, no build needed); if not installed on restore host, restore fails fast with `RuntimeError("pip install cryptography required to decrypt")`
- `exclude_symlinks` still skips symlinks even for secrets (prevents infinite loops)
- Drive folder layout: same relative tree with `.enc` suffix, parent folders resolved via `ensure_folder_path` on original dir (no `.enc` dir)
- `profile_name` always set (validated), so `manifest_path` derivation and `_drive-backup` key path expansion are safe

## Blockers / Residual Risks / Follow-up
- **Drive filename correctness**: fixed via `mkdtemp` + correct basename; if `drive_api.upload_file` ever changes to accept explicit name param, engine could be simplified to pass `filename_enc` directly
- **Prune**: `_manifest_key_exists_locally` checks original path, so stale encrypted entries prune correctly via `drive_file_id` (which is `.enc` file); no suffix handling needed, but verify on real Drive that trash of `.enc` works
- **Permissions**: `chmod 0o600` on POSIX for restored secrets dirs; Windows ACL not set (chmod best-effort); could add `win32security` ACL in future if needed
- **Report strictness**: `tests/test_report.py` now expects exact tuple including new keys; any future report changes must update that test
- **CLI `restore` mock**: `tests/test_cli.py` now requires `decrypt`/`decrypt_key_path` kwargs; any external code mocking `restore_backup` with old signature must update
- **Large secrets**: not streamed; if a secrets dir contains a large file (e.g., `.gemini/history` DB >500 MB), it will be skipped; follow-up could allow `no_size_limit` for `.db` or document raising limit
- **Key rotation**: no rotation logic; if user changes key, old `.enc` files remain undecryptable; follow-up could add `drive-backup --re-encrypt` or document re-upload after key change
- **Concurrency**: `BackupEngine` concurrent pipeline encrypts in worker threads (`_execute_upload` runs in `ThreadPoolExecutor`); `crypto.encrypt_file` is CPU-bound but secrets are small, so GIL impact minimal; no shared key mutation
- **Verification gaps**: real Drive `--dry-run`/`--restore` on Windows host with actual credentials not run in this worktree (no credentials); covered by `FakeDrive` integration; recommend manual smoke on personal laptop before merge: `drive-backup --dry-run --verbose` (key panel, `WOULD_UPLOAD ... (encrypted)`), `drive-backup` (uploads `.enc`, manifest `encrypted:true`), `drive-backup --restore --output /tmp/restore-test` (decrypted byte-identical, `0o600`), then rename key away and restore again (`.enc` with warning)
